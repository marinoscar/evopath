# Email templates

How every transactional email in the application is built, and how to add one.

An email template is a pure function from typed data to a `RenderedEmail`
(`subject`, `html`, `text`, `headers`, `attachments`). A template has no Nest
providers, no database access, no clock and no `await`. The caller gathers the
data and passes it in.

## Files

| File | Holds |
|---|---|
| `layout.ts` | The HTML shell (`renderLayout`), the palette, the components, the timestamp helpers and the plain-text composer (`plainText`) |
| `safe-html.ts` | The `html` tagged literal, `SafeHtml`, `escapeHtml` and `safeUrl` |
| `email-template.types.ts` | `RenderedEmail`, `EmailTemplate`, `TRANSACTIONAL_EMAIL_HEADERS` and `composeEmailMessage` |
| `index.ts` | The registry: `EmailTemplateDataMap`, `EMAIL_TEMPLATES`, `renderEmailTemplate` |
| `brand-mark.generated.ts` | The inline logo bytes. Generated by `apps/web/scripts/generate-icons.py`; never edit it by hand |
| `<name>.email.ts` | One template each |
| `*.spec.ts` | Layout, registry and per-template tests |

## Layout contract

`renderLayout` produces the whole document. Its header comment in `layout.ts`
is the full rationale; the contract is:

- **Tables and inline styles.** Layout is nested `<table role="presentation">`. There is no flexbox and no grid. Every element carries its complete light-mode styling inline.
- **One progressive `<style>` block.** It holds only dark mode (`prefers-color-scheme`, plus the Outlook.com `data-ogsc` and `data-ogsb` equivalents) and the phone breakpoint. Classes (`em-bg`, `em-card`, `em-text`, ...) are hooks for that block and never carry baseline appearance. A client that strips the block still shows a correct message. `layout.spec.ts` fails on any other top-level rule.
- **No remote assets.** No `<link>`, no remote image, no web font, no `http(s):` `src`. The only `src` scheme emitted is `cid:`.
- **The logo is an inline MIME part.** The HTML references `cid:brand-mark`. Every template returns `layoutAttachments()` as `attachments`, and `composeEmailMessage` carries it into the `EmailMessage`. SMTP maps it to a nodemailer `cid` attachment and SES to `Content.Simple.Attachments` with inline disposition. The product name is live text beside the image, and the image has an empty `alt`.
- **A hidden preheader.** `previewText` fills the inbox snippet. Without it the client scrapes the eyebrow and product name, and every message previews alike.
- **A hand-written text part.** `text` is required on `RenderedEmail` and `EmailMessage`. No HTML-to-text function exists. Compose it with `plainText`, `textDetailLines` and `textCallout`, which mirror the HTML components.
- **A palette that survives forced dark mode.** Body text uses near-black or near-white extremes. Mid-tone brand and status colours appear only on short bold accents (eyebrow, callout label, button).
- **A bulletproof button.** A VML button for Outlook on Windows, a table-cell button elsewhere, and the URL printed below as text. A `ctaUrl` that `safeUrl` rejects drops the button from the HTML and the link from the text.

## Layout options

`renderLayout` takes `RenderLayoutOptions`:

| Option | Meaning |
|---|---|
| `title` | Card heading and document `<title>` |
| `eyebrow` | Short category label above the title (`Account`, `Security`, `Operations`, `Announcement`, `Test`) |
| `previewText` | Hidden inbox preview text |
| `bodyHtml` | The body, as `SafeHtml` (a string does not typecheck) |
| `ctaLabel`, `ctaUrl` | The button. Rendered only when both are present and the URL is absolute `http(s)` or `mailto` |
| `secondaryHtml` | Content below the button, such as a `secondaryLink` |
| `footerReason` | Why the recipient got this message |
| `preferencesUrl` | Absolute URL of the recipient's notification preferences; shows "Manage email preferences" in the footer |

## Components

All components return `SafeHtml`. A `string` argument is escaped; a `SafeHtml`
argument is emitted as is.

| Component | Use |
|---|---|
| `paragraph(content, { tone? })` | Body copy; `tone: 'muted'` for supporting copy |
| `detailRows(rows)` | Label/value table. A row is `{ label, value, mono?, datetime? }`. Build instant rows with `timestampRow(label, value)` |
| `callout({ tone, title?, body })` | Tinted state box. Tones: `info`, `success`, `warning`, `critical`. A text label (`Info`, `Done`, `Warning`, `Action needed`) carries the state, so colour is never the only signal |
| `codeBlock(text, { label? })` | Escaped monospaced excerpt that keeps line breaks, for an error message or log line |
| `divider()` | Hairline between sections |
| `secondaryLink(label, url)` | Text link for `secondaryHtml`; an unusable URL drops the line |

Text-part counterparts: `textDetailLines(rows)`, `textCallout({ tone, title?, body })`.

### Example

Condensed from [`job-failed.email.ts`](./job-failed.email.ts):

```ts
import {
  APP_NAME, callout, codeBlock, detailRows, html, layoutAttachments,
  paragraph, plainText, renderLayout, textCallout, textDetailLines, timestampRow,
} from './layout';
import { TRANSACTIONAL_EMAIL_HEADERS, type RenderedEmail } from './email-template.types';

export function jobFailedEmail(data: JobFailedEmailData): RenderedEmail {
  const title = 'Background job failed';
  const eyebrow = 'Operations';
  const footerReason = `You received this because you can view background jobs in ${APP_NAME}.`;
  const facts = [
    { label: 'Job type', value: data.jobType, mono: true },
    timestampRow('Failed at', data.failedAt),
  ];

  const bodyHtml = html`
    ${paragraph('A background job used up its retry budget.')}
    ${callout({ tone: 'critical', title: 'It will not be retried', body: 'Fix the cause, then run it again.' })}
    ${detailRows(facts)}
    ${codeBlock(data.error ?? 'Not recorded', { label: 'Last error' })}
  `;

  return {
    subject: `${APP_NAME}: background job "${data.jobType}" failed`,
    html: renderLayout({ title, eyebrow, previewText: data.jobType, bodyHtml, footerReason }),
    text: plainText({
      eyebrow, title, footerReason,
      lines: [
        'A background job used up its retry budget.',
        '',
        ...textCallout({ tone: 'critical', title: 'It will NOT be retried', body: 'Fix the cause, then run it again.' }),
        '',
        ...textDetailLines(facts),
      ],
    }),
    headers: { ...TRANSACTIONAL_EMAIL_HEADERS },
    attachments: layoutAttachments(),
  };
}
```

Always build the body with the `html` tag. Interpolating a value there escapes
it; concatenating strings does not typecheck against `bodyHtml`.

## Timestamps

Render every instant through the helpers, never through `toLocaleString`,
`toISOString` or the host time zone.

| Helper | Returns |
|---|---|
| `formatEmailTimestamp(value, { seconds? })` | `1 Oct 2026, 02:00 UTC`: always UTC, English month, 24-hour clock |
| `timeHtml(value)` | The same string inside `<time datetime="<ISO>">`, kept on one line |
| `timestampRow(label, value)` | A `detailRows` row; the text part gets the human string, the HTML a `<time>` |
| `formatEmailDuration(start, end)` | `31 s`, `2 min 4 s`, `1 h 5 min`: two units at most; `undefined` when invalid or negative, so omit the row |

The helpers never throw. An invalid input renders unchanged. Pass dates into
the template (`failedAt: Date`) instead of reading the clock inside it.

## Previewing

Render every registered template to local files:

```bash
npx tsx apps/api/scripts/render-email-previews.ts <outDir>
```

The script writes `<template>.html`, `<template>.txt` and an `index.html` that
links them with their subjects. In the HTML, each `cid:` reference becomes a
`data:` URI of the matching attachment, so a browser shows the logo. The sample
data is fixed, so two runs produce identical files. The script needs no
database, no network and no running API.

## Adding a template

1. Create `<name>.email.ts` exporting a data interface (with `appUrl?` when there is a button) and a pure function returning `RenderedEmail`.
2. Set an `eyebrow` that names the category.
3. Set a `previewText` that answers "do I need to open this?" on its own.
4. Set a `footerReason` that says why this recipient got the message.
5. Set a `preferencesUrl` (appended to `appUrl`) for any message the recipient can switch off. Omit it for a mandatory message (a security or privilege change); the existing templates without one are `allowlist-invitation`, `broadcast`, `restore-completed`, `role-changed` and `test-email`.
6. Build the HTML with the layout components and the `html` tag; build the text part by hand with `plainText`.
7. Return `headers: { ...TRANSACTIONAL_EMAIL_HEADERS }` and `attachments: layoutAttachments()`. The attachment is required: without it the header logo is a broken image.
8. Render timestamps with the timestamp helpers, and pass dates in as data.
9. Register the template in `index.ts`: add the entry to `EmailTemplateDataMap`, then to `EMAIL_TEMPLATES`. The compiler rejects half a registration.
10. Map the event key to the template name in `EVENT_EMAIL_TEMPLATES` ([`email-notification.channel.ts`](../../notifications/channels/email-notification.channel.ts)); see the [notifications README](../../notifications/README.md).
11. Add sample data to `SAMPLES` in `apps/api/scripts/render-email-previews.ts`. `SAMPLES` is a total map over the registry, so a missing sample is a compile error.
12. Add a spec `<name>.email.spec.ts` for what is specific to the template: its facts appear in both parts, hostile input is escaped in the HTML and left raw in the text, and a dropped optional field leaves no stray label. `index.spec.ts` already runs every registered template through the shared contract.
13. Run the preview script and open the output in a browser, in light and dark mode.
